# プレイブック — ハイブリッド開発（段階昇格型）の運用

このリポジトリの開発は「案4: ハイブリッド型（段階昇格型）」で進める。
試作は軽い場所で速く作り、育てると決めたものだけを本格構成へ昇格させる。
司令塔は常に iPhone。人間は依頼・判断・承認を行い、実装と検証は Muse が行う。

## 1. 2つの場所と役割

| 場所 | 役割 | 向いているもの |
|---|---|---|
| Muse スペース / VM ワークスペース | 試作・検証 | 個人用ツール、ダッシュボード、使い捨ての検証、学習 |
| このリポジトリ (GitHub) | 正本・本格開発 | 長く育てるもの、公開するもの、失敗したくないもの |

- 試作側にコードの正本を置かない。残す価値が出たら、早めにこのリポジトリへ移す
- 仕様の正本は、このリポジトリの `docs/` とする（Google Docs は共有・閲覧用に使ってよいが、正本はここ）

## 2. 試作から始める場合の流れ

1. iPhone で要件を伝える
2. Muse が Muse スペース等で試作を作り、触れる形で返す
3. 使ってみて、残すかどうかを判断する（目安は次節の昇格基準）
4. 残す場合: 仕様を `docs/` に起こしてから、リポジトリで作り直すか移行する

## 3. 昇格基準 — 次のどれか1つに当てはまったら昇格する

- [ ] 自分以外の人も使う（家族・顧客・不特定多数）
- [ ] お金、個人情報、業務データを扱う
- [ ] 公開 URL が必要（誰かにリンクで渡す、常時公開する）
- [ ] 数週間以上にわたって使い続ける見込みがある
- [ ] 壊れたり失ったりすると困る

当てはまらないものは試作側に置いたままでよい。ただし試作のまま肥大化させない。
仕様だけ大きくなってきたら、コードより先に仕様をこのリポジトリへ移す。

## 4. 昇格チェックリスト

- [ ] 仕様を `docs/spec-template.md` の形で `docs/` に書いた
- [ ] プロジェクト用フォルダを切り、試作コードを移植または作り直した
- [ ] ローカル/VM で動作確認し、結果を記録した
- [ ] 技術選定（言語・フレームワーク）を決め、CI (GitHub Actions) を設定した
- [ ] 公開が必要な場合: 公開先（ホスティング）を決め、秘密情報はリポジトリに入れず設定側に置いた
- [ ] README にプロジェクトの目的と動かし方を書いた

## 5. 日常の開発サイクル（リポジトリ側）

1. 依頼（iPhone）→ Muse が仕様と作業分解を提示
2. チェックポイントで承認
3. ブランチを切って実装（ブランチ名は `AGENTS.md` の規約どおり）
4. テスト・動作確認を行い、結果つきで報告
5. プルリクエストを作成し、要約・差分・確認結果を提示
6. 人間がマージを承認

報告は「終わったもの / 残っているもの / 次にすること」の3点で行う。

## 6. プロジェクト開始時に決めること（事前に決めない）

次は最初のプロジェクトと同時に決める。今ここで作っても空回りするので作らない。

- CI の具体的なテスト内容（技術選定に依存）
- 公開先ホスティングと、その接続・秘密情報の設定
- VM 上でコードを実行・テストする際のリポジトリ同期手順（最初の1周で固める）
- 公開後の見張り（CI 失敗・デプロイ失敗の通知）が要るかどうか

## 7. 安全の境界

- 秘密情報はコミットしない。`.gitignore` の除外を維持する
- マージ、公開・デプロイ、外部送信、削除、課金は人間の承認を経る
- `main` への直接プッシュはしない（リポジトリ初期構築のみ例外とした）
